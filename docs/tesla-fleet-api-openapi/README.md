# Tesla Fleet API (Official) — OpenAPI spec

Tesla's **official, currently-supported** developer API (developer.tesla.com). This is the
successor to [`../tesla-api-openapi/`](../tesla-api-openapi/) (the unofficial owner-api flow),
which Tesla began actively rejecting (`redirect_uri not registered`) around April-May 2026 —
see that folder's README for the details that led here.

Generated by reading the source of the actively-maintained open-source client library
[Teslemetry/python-tesla-fleet-api](https://github.com/Teslemetry/python-tesla-fleet-api)
(precise working request/response shapes as of 2026-08-16), not scraped prose docs.

## What's in here

| File | What |
|---|---|
| `openapi.yaml` / `openapi.json` | 113 paths / 116 operations: Authentication, API Basics, Users, Charging, Vehicle State, Vehicle Commands, Sharing, Fleet Telemetry, Energy Products. |
| `index.html` | Swagger UI, points at `openapi.yaml`. |

## Before ANY of this works: one-time setup at developer.tesla.com

Unlike the old owner-api flow, there's no shared client_id — every app needs its own real
registration. In order:

1. **Create a developer account** at [developer.tesla.com](https://developer.tesla.com).
2. **Register an application** to get your own `client_id` / `client_secret`.
3. **Register a real `redirect_uri`** for your app (exact match required — e.g.
   `https://your-domain.example.com/api/v1/auth/callback`). The old shared
   `https://auth.tesla.com/void/callback` trick does not work here.
4. **Host your public key** at
   `https://<your-domain>/.well-known/appspecific/com.tesla.3p.public-key.pem` on a domain you
   control.
5. **Get a partner (app-level) token**: `POST /oauth2/v3/token` with `grant_type=client_credentials`
   — see the `exchangeCodeForToken` operation's `client_credentials` example in the spec.
6. **Register your domain**: `POST /api/1/partner_accounts` with that partner token — see
   `registerPartnerAccount`.
7. Only now can real users authorize your app (`getLoginPage` → `exchangeCodeForToken` with
   `grant_type=authorization_code`) and vehicle/energy calls start working.

## Key differences from the old owner-api spec

- **No PKCE.** This is a confidential OAuth2 client (real `client_secret`), not code_challenge/verifier.
- **Path param is `vin`**, not `vehicle_id` — and it's the actual VIN string, not a numeric ID.
- **Energy site path param is `energy_site_id`**, not `site_id`.
- **Three regional servers** (`fleet-api.prd.{na,eu,cn}.vn.cloud.tesla.com`) — call `getUserRegion`
  right after authenticating to find which one your account should use; don't hardcode a region.
- **Token issuance is a different host** (`fleet-auth.prd.vn.cloud.tesla.com`) than the login page
  (`auth.tesla.com`) — both different again from the main API servers.
- Two multiplexed "catch-all" endpoints worth knowing about:
  - `signedCommand` (`POST /api/1/vehicles/{vin}/signed_command`) — opaque signed-protobuf relay
    for newer vehicles requiring command signing (Tesla's vehicle-command SDK produces the payload;
    not something to hand-construct).
  - `sendEnergyDeviceGrpcCommand` (`POST /api/1/energy_sites/{energy_site_id}/command`) — backs
    ~20 undocumented energy-gateway commands (get_system_info, wifi_scan, add_authorized_client,
    etc.), all multiplexed through one endpoint via a `category`/`command` pair — see that
    operation's description for the full catalog.
